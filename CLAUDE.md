# CLAUDE.md — OpenClip Support for ComfyUI

## Solution Overview

To simplify integration of ComfyUI into VFX pipelines, a set of read/write nodes that are
based on the OpenClip standard makes renders and version management easier.

### Requirements

- Support the latest OpenClip standard by Autodesk (version 8 and 9)
- Support reading of PNG and OpenEXR sequences
- If possible include the JSON file of the ComfyUI workspace when writing a 'published' OpenClip
- All the controls existing for OpenClip in Flame (versioning, etc.)
- All the controls existing in current Read/Write nodes of ComfyUI (frame ranges, etc.)
- Ability to handle alpha channels
- Reader outputs start_frame, clip_path, clip_name, and version_name so they can be wired directly into the Writer for round-trip workflows without retyping
- Writer accepts a clip_filename pattern (`$(path)/$(clip_name)`) to compose the output destination from wired inputs with optional prefixes/suffixes
- EXR header metadata (tape name, timecodes, scene/take, etc.) extracted on read and optionally carried through to written files via a CLIP_METADATA output/input pair
- Writer defaults to always writing the next available version (Flame-style version safety) and refuses to silently clobber an existing version unless the artist explicitly opts in
- Lossless fp16/fp32 round trip with no implicit clamping to 0..1 anywhere in the EXR read/write path, and AOV pass-through (normals, world normals, depth) as separate typed outputs/inputs, addressed strictly by channel name — see `EXR_REQUIREMENTS.md` (requirements driven by the sister `ComfyUI_Harmonize` project, which depends entirely on this repo for EXR/Open Clip I/O)

## Architecture Decisions

### Design Choices

| Concern | Decision | Rationale |
|---|---|---|
| Workflow direction | Full round-trip (read + write) | Clips flow from Flame → ComfyUI for processing and back |
| OpenClip version compat | Detect on read; round-trip same version | Preserves schema fidelity; no silent upgrades |
| OpenClip write version | Always v8 | v9 not yet released by Autodesk |
| XML structure on write | Flame-compatible structure | `<trackType>`, `<editRate>`, full `<storageFormat>` with dimensions/depth, `<sampleRate>`, `<startTimecode>`, `<versions>` block |
| Package layout on write | Configurable: Standard Flame or Flat | Pipeline needs vary; Standard Flame safe for direct library scan |
| Alpha channel | Optional MASK input merged as RGBA EXR alpha | Matches ComfyUI's IMAGE/MASK tensor convention |
| Publish (workspace JSON) | Sidecar `.comfy.json` + path reference in XML | Inspectable on disk; mirrors Flame "publish" concept for artists |
| Image I/O | OpenImageIO (OIIO) | Handles EXR and PNG in one library; full multi-part and deep EXR support |
| Distribution | ComfyUI Manager custom node pack | One-click install; still works as manual copy to `custom_nodes/` |
| Round-trip wiring | Reader outputs start_frame, clip_path, clip_name, CLIP_METADATA, fps | Direct connections to Writer avoid retyping and prevent numbering drift |
| Writer destination | `clip_path` + `clip_name` + `clip_filename` pattern replaces flat `output_dir` | `$(path)`/`$(clip_name)` tokens allow suffixes without breaking wired connections |
| `clip_filename` token syntax | Explicit parentheses: `$(path)`, `$(clip_name)` (not bare `$path`/`$clip_name`) | Prevents adjacent literal text (e.g. `$(clip_name)_clean`) from being mistaken for part of the token name if more tokens are added later |
| `clip_filename` scope | Same expanded name is used for the `.clip` file *and* the media sequence filenames | Both come from `package_layout.build(clip_name=...)`; there's no way to rename just the `.clip` file independently of the frames |
| EXR metadata carry | CLIP_METADATA type (Python dict of OIIO extra_attribs) | Optional; only applied when input is connected; writer format attrs always win |
| Version in frame filenames | `include_version_in_filename` checkbox (not a `clip_filename` token) | A `$(version)` token in `clip_filename` would change the `.clip` filename per version too (since that name is shared, see `clip_filename` scope above), breaking multi-version merge into one `.clip` file; a separate boolean keeps the `.clip` filename stable while still disambiguating frames on disk (`Flat` layout reuses one directory across versions with no other disambiguator) and matches Flame's own `name.version.####.ext` convention |
| FPS type on Reader/Writer | `FLOAT`, not `COMBO`/`STRING` | Lets other ComfyUI nodes (which commonly use plain `FLOAT` for fps) wire directly; NTSC rates (23.976, 29.97, 59.94) are exact rationals internally (e.g. 24000/1001), so Reader outputs the true rational value and Writer matches an incoming float to the nearest supported rate within tolerance (`openclip_xml.fps_label_from_float`) rather than doing exact/decimal comparison |
| Reader schema-version output naming | `format_version` (was `clip_version`) | The old name collided conceptually with the (now removed) `OpenClipVersionSelector`'s `selected_version`/`current_version` (feed versions like `v002`), even though this output is the OpenClip **schema** version (`"8"`/`"9"`, the root `<clip version="…">` attribute) — an artist saw `format_version="9"` next to a selected feed version and assumed it was a bug |
| Version selection lives on Reader, not a separate node | `OpenClipVersionSelector` removed; Reader gained `OUTPUT_NODE = True`, a `version_name` output (resolved actual version, e.g. `v002` — never the literal `"current"`), and kept the `available_versions` STRING output | One fewer node to wire for the common case (browse versions, then load one); `OUTPUT_NODE = True` lets an artist queue-prompt the Reader alone to inspect a clip's versions without wiring anything downstream, the way `OpenClipVersionSelector` worked standalone. Writer already had a `version_name` input, so `Reader.version_name → Writer.version_name` lets the Writer follow the Reader's numbering on request. Breaking change: any saved workflow JSON still containing an `OpenClipVersionSelector` node shows as a missing node when reopened — accepted as a one-time cost since this is early-stage, single-pipeline tooling. |
| In-node version list display | `web/openclip_reader.js` writes `available_versions` into a read-only multiline widget via the node's `onExecuted` callback, **plus** `available_versions` stays a normal STRING output | Satisfies "see the list without a separate preview node" while keeping a zero-JS fallback. This is a different mechanism than what broke `OpenClipVersionSelector` before (that used `widget.draw`/`mouse` overrides + a custom button + a custom `/openclip/versions` API route); this instead uses the same execute-time `onExecuted(message)` hook that ComfyUI's own image-preview nodes rely on. Still custom JS, still carries some risk on a future frontend rewrite — hence the output fallback is mandatory, not optional, per explicit user decision. |
| Reader `load_alpha` toggle | Removed; Reader always loads the alpha channel into MASK when the source has one | An artist hit a silent black-mask bug from leaving the (default-off) toggle unchecked on an RGBA source. `image_io.read_sequence` already reads all channels regardless of the flag and only slices differently, so there is no I/O cost to always attempting alpha; a 3-channel source still yields a zero-filled MASK exactly as before. The underlying `image_io.read_sequence(..., load_alpha: bool)` parameter is kept — it's a reasonable lib-level control and existing tests exercise both branches directly. |
| Reader cache invalidation | `OpenClipReader.IS_CHANGED()` hashes the `.clip` file's + first resolved frame's `(mtime_ns, size)` | ComfyUI only re-executes a node when its `IS_CHANGED()` classmethod returns a different value than last run (confirmed against ComfyUI's `execution.py`/`comfy_execution/caching.py`); without it, an artist re-rendering a clip on disk with the same `clip_path`/`version`/frame range saw a stale cached image until a server restart. Deliberately checks only the `.clip` file and the first frame, not every frame in the range, to keep the check cheap on long sequences — a re-render that changes only a middle/late frame without touching the `.clip` file or frame 1 (e.g. re-rendering a handful of flagged frames on a farm) would not be detected; explicit user decision to accept that gap for the cheaper check. |
| Colour transform pipeline | `apply_colour_transform()` uses `ocio.DisplayViewTransform(src, display, view)` instead of `config.getProcessor(input_space, output_space)` | The plain-`getProcessor` form connects directly to a *display-referred* colour space, which in an OCIO v2/ACES config is encoding-only (EOTF + primaries) — it skips the View's ACES Output Transform (tone-mapping/gamut compression) entirely. Confirmed against the Academy's public reference ACES 2.0 config (same one Flame's `aces2.0_config` ships unmodified): a saturated red came out with a negative channel and a value above `1.0` via the old path, vs. correctly compressed into range via `DisplayViewTransform`. This matched the reported symptom exactly (bad reds; a downstream model hallucinating on out-of-range pixel values) and matched why bypassing the node with Flame's own view-transformed render worked. Added a new `view` node input (default `"ACES 2.0 - SDR 100 nits (Rec.709)"`, `lib.colour_transform.OUTPUT_VIEW`) rather than hardcoding a view, so an artist can pick alternate views (`Un-tone-mapped`, HDR, etc.) the way Flame lets them pick a view transform — explicit user decision over auto-picking the config's default view. Breaking change: saved workflows need the new `view` input filled in, same one-time cost as the `load_alpha`/`OpenClipVersionSelector` changes. |
| Writer version collision handling | New `overwrite` `BOOLEAN` input, default `False`. On collision (resolved `version_name` already present in the `.clip`), `False` raises a `ValueError`; `True` deletes that version's existing frame files (`_delete_existing_frames`, glob on the frame stem so a shorter re-render leaves no stale trailing frames) then replaces the XML `<version>`/`<feed>` entry | An artist hit this in real usage: re-wiring `Reader.version_name → Writer.version_name` to re-process the same version re-triggers the exact collision this guards against, so overwrite exists specifically to make that wiring safe when intentional. Defaults to `False` because Flame artists treat overwriting a version as a deliberate, not incidental, act — explicit user decision. Frame deletion happens before the new frames are written, not after, so a render that produces fewer frames than the one it replaces can't leave orphaned old frames behind (explicit user decision, "delete old frames first" over "leave old frames in place"). |
| Writer default/auto version selection | `version_name` default changed from `"v001"` to `"next"`; `"next"` is a Writer-only sentinel (mirrors the Reader's `"current"` sentinel) resolved via `openclip_xml.next_version()`, which reads the existing `.clip` XML and returns one past the highest `v<NNN>`-named version present (`v001` if the clip doesn't exist yet or has no numbered versions) | Satisfies "Writer should always write the next available version" without Flame's stateful behaviour (which auto-increments a widget after a successful write) — that would require the same kind of custom frontend JS (`widget`/state mutation on execute) that already broke the removed `OpenClipVersionSelector` once. Resolving statelessly from the XML on every run is idempotent, survives ComfyUI restarts, and needs zero JS — explicit user decision over the stateful Flame-parity option. A brand-new Writer node therefore defaults to `"next"` and just works; wiring `Reader.version_name` in (or typing an explicit name) opts back out of auto-selection, per the existing round-trip convention. |
| Writer error message on version collision | Kept as a plain `ValueError` (no custom UI/JS popup) with an explicit `VERSION ALREADY EXISTS` banner line and a "fix by one of" list (`use 'next'` / `enable overwrite` / `type a different version_name`) | An artist reported ComfyUI's existing error surface (it does show node-execution exceptions in the UI) as "hidden and not very distinguishable from other errors" — the fix was making the message itself unmistakable and actionable, not building a new notification mechanism. A custom popup would mean more frontend JS with the same fragility already flagged for the version-list widget above; explicit user decision to avoid that for a message-content problem. |
| AOV output shape on Reader | Fixed named outputs (`NORMAL`, `NORMAL_WORLD`, `DEPTH`), not a generic dict/type | Matches `EXR_REQUIREMENTS.md`'s exact convention table (beauty, `N`, `Nw`, `Z`); wires directly into typed downstream sockets (e.g. Harmonize's `SHFitLighting`) with no unpack node. Explicit user decision over a generic `AOV_DATA` dict, which would be more extensible to future layers (e.g. Cryptomatte, seen in real production material) but can't wire directly into a typed socket. |
| AOV discovery for the separate-file layout | Fixed suffix convention (`_AOV_Normals`, `_AOV_NormalsWorld`, `_AOV_Depth`), not configurable suffix inputs | Matches `ComfyUI_Harmonize/tests/generate_synthetic_exr.py` exactly (the reference fixture generator EXR_REQUIREMENTS.md says to build against). Real production material on the share (`CarInterior_AOV_*`) uses messier, inconsistent naming (e.g. a stray space) — not chased in this phase; explicit user decision. Auto-detected on every Reader run (multichannel file checked first, then sibling files, then — since 2026-08-22 — `None`; see "Missing AOV behaviour" below) — no new toggle, matching the precedent that killed the old `load_alpha` toggle (silent-default-off bug class, see below). |
| Channel-by-name discipline in `image_io.py` | All channel access (R/G/B/A and AOV groups) resolved via `spec.channelnames`, never a fixed index | OpenEXR does not preserve channel write order and OIIO reorders on read — verified empirically against the installed OIIO 3.1.15: writing `R,G,B,A,N.X,N.Y,N.Z,Nw.X,Nw.Y,Nw.Z,Z` reads back as `R,G,B,A,Z,N.X,N.Y,N.Z,Nw.X,Nw.Y,Nw.Z` (`spec.channelindex('N.X')==5`). The pre-AOV code sliced `pixels[:, :, :3]`/`[:, :, 3]` positionally for R/G/B/A — reworked to resolve every channel group by name (`_extract_named_channels`), since a multichannel AOV file would otherwise have silently misattributed channels (depth in the normal-X slot) with a plausible-looking wrong result — exactly the failure mode `EXR_REQUIREMENTS.md` #5 warns about. |
| Missing AOV behaviour | **Changed 2026-08-22:** `None` when a layer was never found in *any* frame of the requested range, not a zero-filled tensor. Any individual frame within an otherwise-present AOV that lacks that one frame's layer is still zero-filled — this is a per-sequence signal, not a per-frame one. | Found reading this code for `ComfyUI_Harmonize`'s new `NormalsRouter`/`DepthRouter` (a "use the real map if one exists, else generate one" node whose entire premise depends on being able to tell "missing" apart from "present"): the original zero-fill design (below) makes that impossible from the output tensor alone — a genuinely absent AOV is indistinguishable from one that's present and legitimately all-zero. `read_sequence_with_aovs()` already computed this per-frame (`_read_frame()` returns `None` per AOV per frame) but discarded it before returning; now tracks a `found` flag per AOV key across the frame loop and returns `None` for the whole key when it's never true. `OpenClipReader.execute()` needed no change — it already just returns `aovs[key]` directly, so `None` flows straight through as the node output. Verified against real OIIO on akflame5 (this repo's local pytest run has no OIIO — see `tests/CLAUDE.md`): a standalone script, same fixture-writing helpers as `tests/conftest.py`, covering `read_sequence_with_aovs()` directly and a full `OpenClipWriter`→`OpenClipReader` round trip at the node level. Existing zero-fill assertions in `tests/test_image_io.py`/`tests/test_system.py` updated to assert `is None` instead. **Breaking change:** any existing graph wiring a Reader `NORMAL`/`NORMAL_WORLD`/`DEPTH`/`NORMAL_RAW` output straight into a node that assumes a real tensor (not just passing it through to another optional socket) will now get `None` instead of harmless zeros wherever that AOV is actually absent, and will error unless the downstream node tolerates `None`. Checked Harmonize's `realplate_moduleA.json` specifically: none of its Reader AOV outputs are currently wired to anything (Lotus generates normals there instead), so it's unaffected — but this wasn't checked against every saved workflow, and none of Harmonize's own nodes were changed to *require* this new contract at the same time (that's the still-unbuilt `NormalsRouter`/`DepthRouter` — see `ComfyUI_Harmonize/CLAUDE.md`). |
| Missing AOV behaviour (superseded 2026-08-22, kept for history) | Zero-filled tensor at the beauty frame's H×W, whole-group-or-nothing (no partial fill) | Same precedent as the existing MASK-for-missing-alpha behaviour (see "Alpha Channel Handling" below). No fabricated "far" depth value on absence — that's a synthetic-fixture detail (`generate_synthetic_exr.py`), not something the Reader invents when a layer is genuinely not present. |
| Multi-part EXR reads: part-name convention | `_read_frame()` walks subimages beyond 0 via `seek_subimage()`, matching each part's `name` attribute against `depth_part_name`/`normal_world_part_name`/`normal_raw_part_name` (new Reader `STRING` inputs); only a matching part is pixel-decoded | `EXR_REQUIREMENTS.md` had flagged "single-part dotted vs. true multi-part" as unconfirmed. An artist's real Flame multi-layer render (beauty + depth + normals + Cryptomatte) confirmed it's multi-part, but **not** with dotted channel names as first assumed — every part just uses generic `R,G,B`, and the AOV's identity is carried only by the part `name` (confirmed via `oiiotool --info -v -a`). This is because the AOVs were imported into Flame from another DCC (Cinema 4D), never generated by Flame itself, so this project's own dotted-layer.channel convention never applied to that data. Since Cryptomatte's channels are *also* just `R,G,B`, it's indistinguishable from a real AOV by channel name alone — matching by part name instead (not channel name) is what keeps a heavy Cryptomatte part from being needlessly pixel-decoded, addressing the deferred AOV-performance flag (#7) below for this case. Depth's data is a replicated scalar across R/G/B (verified empirically: `R==G==B` everywhere in the real file) — channel 0 is read as the value. |
| Ambiguous normal space (`normal_raw`) | New Reader output `NORMAL_RAW` (`IMAGE`), fed by `normal_raw_part_name` (default `"normals"`) — distinct from the existing space-committed `NORMAL`/`NORMAL_WORLD` outputs, which stay zero-filled unless a distinctly-named part or the dotted-channel convention actually identifies the space | Explicit user decision, arrived at after finding the real file has exactly one ambiguous normals-like part with no way to determine camera vs. world space (the data didn't originate in Flame). Populating `NORMAL` or `NORMAL_WORLD` with unverified-space data would be silently, plausibly wrong — exactly the failure class this whole feature exists to prevent. The toggle to declare/relabel the space is explicitly **not** added here; it's Harmonize's job (a new Harmonize-side node), keeping this repo's Reader mechanical (an explicit user decision made when this was discovered — see git history around this table entry). Writer does not yet accept a `NORMAL_RAW` input — writing the part-name convention back out (multi-part EXR with named parts) is unimplemented; round-tripping this AOV isn't currently possible and is a known gap, not a silent no-op (there's no `NORMAL_RAW` Writer input to wire it into, so a workflow can't silently drop it without a missing-connection warning). |
| Writer AOV write support | Optional `NORMAL`/`NORMAL_WORLD`/`DEPTH` inputs plus an `aov_layout` combo (`Multichannel` default, `Separate Files`), mirroring the Reader's dual-layout read support | Explicit user decision: `EXR_REQUIREMENTS.md` requirement #5 is phrased read-oriented, but Harmonize's own round-trip needs to write AOVs back out too, not just read them through. AOV inputs with `file_format="PNG"` raise `ValueError` — PNG's 8-bit clamp-to-uint8 path would silently corrupt normals (which are signed, roughly -1..1) or depth (unbounded), the same silent-wrong-data failure class this whole feature is about. |
| AOV performance (fp32 4K sequences, requirement #7) | No skip-AOVs toggle added | AOV tensors add up to 7 extra float32 channels per frame batch (`N`+`Nw`+`Z`) on top of beauty+alpha's 4 — inherent to the feature, not engineered around here. Flagged rather than solved: if VRAM becomes a real constraint under Harmonize's 48GB target, a future opt-in toggle to skip AOV loading could be added, but that's speculative complexity not currently asked for. |
| Lossless fp16/fp32, no clamping (`EXR_REQUIREMENTS.md` requirement #1) | No second "unclamped" `IMAGE` pipe type; the existing `IMAGE` output already carries full unclamped range | Verified the EXR read/write path in `image_io.py` never clamped to begin with (`oiio.FLOAT` read, straight float32 cast on write — only PNG legitimately clamps, being 8-bit). Also verified against ComfyUI's own public source (`comfyanonymous/ComfyUI` `nodes.py`) that clamping is a **per-node** behaviour (core `SaveImage`/`PreviewImage`'s own `np.clip(255*image, 0, 255)`), not something the `IMAGE` socket type itself enforces — so a second type would only protect graphs that explicitly adopt it, and Harmonize's own nodes are typed plain `IMAGE`. Building a second type here would be speculative complexity for a hazard this repo doesn't cause and can't fix from its side of the graph. Locked in with regression tests (`test_exr_round_trip_does_not_clamp`, `test_png_write_does_clamp_intentionally`) instead; artists should avoid routing `OpenClipReader`'s `IMAGE` output through display-referred nodes (core `SaveImage`/`PreviewImage`, third-party "Clamp" utility nodes) without an explicit tone-map step first. |
| `colour_space` output source | EXR header attribute, not the `.clip` XML's `<colourSpace>` element | Verified against the real Flame `.clip` corpus (105 files, schema versions 6–9): XML `<colourSpace>` values are display/timeline-referred (`"Rec.709 video"`, `"Matte"`, `"Raw"`), never camera/ACES scene-referred spaces — the wrong source for `EXR_REQUIREMENTS.md` requirement #3 ("camera log profiles", "ACEScg"). |
| `colour_space` metadata key | Stashed verbatim under a project-namespaced `openclip:ColorSpace` key on write, in addition to the conventional `oiio:ColorSpace`; Reader prefers the former, falls back to the latter | **Verified against the installed OIIO 3.1.15**: its EXR plugin treats `oiio:ColorSpace` as an enum tied to its internal OCIO built-in-config registry, not a free string — on write, recognized names get silently renamed to their canonical form (`"ACEScg"` → `"lin_ap1_scene"`, `"Linear"` → `"lin_rec709_scene"`) and unrecognized ones (arbitrary camera log profile names, show-specific LUT names — exactly what requirement #2/#3 need to carry) are **silently dropped entirely**, no error. This was caught empirically while implementing the `colour_space` output, not anticipated by `EXR_REQUIREMENTS.md` or the original plan — the plain `oiio:ColorSpace` key is still read/populated (for third-party files, e.g. real Flame/camera EXRs, that only carry the conventional key), but this repo's own write path never relies on it alone for round-tripping. |

## Known Issues / Deferred

Real bugs and gaps found but not yet fixed, so they don't get rediscovered from scratch or silently reintroduced.

- **`OpenClipReader`'s `colour_space` output comes back empty for real Flame exports.** Found 2026-08-20 debugging Harmonize's `realplate_moduleA.json` against real `duck_fg.clip`/`duck_bg.clip` files: both have `<colourSpace>ACEScg</colourSpace>` in their Open Clip XML ([reader.py:108](nodes/reader.py#L108) reads `metadata.get(image_io.COLOUR_SPACE_BACKUP_KEY) or metadata.get(image_io.COLOUR_SPACE_KEY, "")`, i.e. only the EXR frame's own OIIO metadata, `oiio:ColorSpace`/`openclip:ColorSpace` — never the Open Clip XML's `colourSpace` tag that `lib/openclip_xml.py:170` already parses), but the reader's `colour_space` output was `''` for both, because these real EXR frames apparently don't carry that OIIO key themselves even though the wrapping XML does. Confirmed live against the actual files, not assumed. Impact: `OpenClipColourSpaceTransform`'s `Same as input (via pipe)` option (added 2026-08-20, see `nodes/CLAUDE.md`) would fail loud (a clear `ValueError`, not silently wrong) rather than resolve, for any real Flame export shaped like these. Fix would be falling back to the Open Clip XML's own `colourSpace` tag when the EXR-level metadata is missing — not done yet, no repro fixture built for it either.
